# AI 工具管理后台 —— 部门级 AI 用量与研发效能看板设计方案

> 版本 v1.0 ｜ 交付形态：前端页面（React + TypeScript）+ 后端聚合服务（Python）
> 数据现状：**企业接口暂无数据**，当前以 mock 数据完整跑通全链路，字段口径与接口文档逐字对齐

---

## 1. 目标与范围

### 1.1 业务目标

回答管理层最关心的四个问题：

| # | 问题 | 对应看板能力 |
|---|---|---|
| 1 | **钱花在哪了** —— 一定时间段内各部门的 AI 用量消耗是多少、环比是涨还是跌 | 用量总览 + 部门效能页的 Credits 消耗、人均消耗、消耗占比、消耗环比 |
| 2 | **花得值不值** —— 消耗有没有转成真实的代码产出 | 千行成本（Credits/千行）、消耗-产出四象限、高耗低产部门识别 |
| 3 | **谁在用、用得多深** —— 每个人的提交代码行数、AI 生成占比、采纳率 | 个人效能页逐人明细 + 成员详情抽屉 |
| 4 | **额度够不够、要不要治理** —— 哪些人/部门有超限风险 | 额度管理页风险分档 + 批量调整 |

### 1.2 明确不做（本期）

- 不做代码仓库（Git）对账：代码行数直接采用企业接口已有的「新增代码总行数」口径，不接入 commit/diff 数据。
- 不做 996/工时类考勤分析：只用 AI 行为数据，不做行为监控。
- 不做自动扣费/充值：额度页只做「调整 + 预警」，充值流程仍走企业资源管理。
- 不做个人绩效结论：页面提供的是**效能证据**，不直接输出考核排名结论（详见 §5.6 伦理边界）。

## 2. 指标口径（先定口径，再画页面）

看板最容易失败的地方不是图表不好看，而是**同一个数在不同页面对不上**。因此先固化四条原则：

1. **先求和再相除**：所有比率（AI 代码占比、采纳率）都由聚合后的分子/分母相除得出，绝不取个人比率的算术平均（避免辛普森悖论）。
2. **部门 = 成员之和**：部门级与公司级指标一律由成员日粒度求和得到，保证「部门汇总之和 == 公司总量」。
3. **消耗与产出成对出现**：任何展示占比的位置都必须能同时看到 Credits 消耗与绝对产出量。
4. **环比区间等长**：环比对照周期与当前窗口严格等长且紧邻（近 30 天 vs 前 30 天）。

### 2.1 核心指标表

| 指标 | 字段 | 公式 | 数据来源（document.yaml） |
|---|---|---|---|
| 用量消耗 | `credit` / `totalUsed` | Σ 对话+补全+生成消耗 | `usage/members/query` |
| 新增代码行数 | `totalNewCodeLines` | 补全采纳行 + 生成插入行（去重） | `dashboard/member/data` |
| AI 生成代码行数 | `aiGenerateCodeLines` | AI 参与生成并保留的行数 | `dashboard/member/data` |
| **AI 代码占比** | `codeGenerateRateByLines` | AI 生成行 ÷ 新增总行数 ×100% | `dashboard/member/data` |
| 补全采纳率（按行） | `completionAcceptRateByLines` | 采纳行 ÷ 生成行 ×100% | `dashboard/member/data` |
| 千行成本 | `creditsPerKline`（派生） | Credits ÷ (新增行/1000) | 由上述两者派生 |
| 额度使用率 | `__quotaUsageRate`（派生） | 窗口消耗 ÷ 周期限量 ×100% | `usage/members/query` |
| Token 消耗 | `token_usage` | 输入 + 输出 token | `observability/metric-summary` |
| 活跃人数 / 日均活跃 | `activeUserNum` / `dau` | 窗口内去重活跃成员数 / 日均 | `dashboard/analytics/activity` |
| 请求失败率 / 首 Token 时延 | `genai_request_error_rate` / `ttft_*` | APM 口径 | `observability/metric-summary` |

### 2.2 三个关键判断的推导方式

**判断一：这个部门是不是「高耗低产」？**
取各部门 Credits 中位数与 AI 代码占比中位数做十字分界，形成四象限：

| 象限 | 判定 | 建议动作 |
|---|---|---|
| 规模双高 | 消耗 > 中位数 且 占比 > 中位数 | 深度使用，关注额度供给与稳定性 |
| **高耗低产** | 消耗 > 中位数 且 占比 < 中位数 | **重点复盘**：采纳率、模型选择、提示质量 |
| 低耗高产 | 消耗 < 中位数 且 占比 > 中位数 | 最佳实践样板，横向推广 |
| 待激活 | 两者均低于中位数 | 渗透率有提升空间，做场景引导 |

**判断二：个人是「真提效」还是「在消耗额度」？**
同时看三个数：`AI 生成行`（绝对值）、`AI 代码占比`（效率） 、`千行成本`（经济性）。
- 行数高 + 占比高 + 千行成本低 → 标杆；
- 消耗高 + 占比低 / 千行成本高 → 待复盘（页面「高消耗待复盘」卡片自动列出）。

**判断三：额度要不要提？**
风险分档：使用率 ≥90% 超限风险（红）、70~90% 偏高（黄）、<70% 正常（绿）、不限量（灰）。
提额前先确认该成员是否属于「高耗低产」，避免为低效使用继续加额度。

### 2.3 口径边界（必须向业务方说明）

- **AI 代码占比 ≠ 提效幅度**：占比高只说明采纳多，行数受语言与格式化影响（SQL/Markdown 单行差异大）。
- **额度周期 ≠ 看板窗口**：额度周期可能是自然月或订阅生效日切片（`cycleMode`），与「近 30 天」不一定对齐，提额决策以额度周期为准。
- **私有化/无 APM 时**：可观测域指标返回 404 属预期降级，前端必须展示「该指标不可用」而不是 0。
- **非编码岗位**：产品/运营不产出代码，千行成本会失真，需按部门类型区别解读。

## 3. 技术架构

```
┌──────────────────────────────────────────────────────────────┐
│  浏览器  React 18 + TypeScript + Vite + Tailwind + ECharts    │
│  ├─ ScopeContext  全局筛选（时间范围 / 部门范围）单一事实来源   │
│  ├─ lib/api.ts    强类型数据访问层（页面不感知 mock / live）    │
│  └─ pages/        总览 · 部门效能 · 个人效能 · 额度管理 · 口径   │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTP /api/...（Vite 代理到 127.0.0.1:8000）
┌───────────────▼──────────────────────────────────────────────┐
│  Python 后端（标准库，零依赖）                                  │
│  ├─ DataSource    数据源抽象：mock JSON ⇄ 企业 OpenAPI 客户端   │
│  ├─ metrics.py    唯一聚合实现：成员日粒度 → 部门/公司 rollup    │
│  └─ server.py     路由 + 口径校验 + 自检                        │
└───────────────┬──────────────────────────────────────────────┘
                │
     ┌──────────▼──────────┐        ┌───────────────────────────┐
     │ data/mock_dataset   │  或    │ 企业 OpenAPI（暂未就绪）    │
     │ 180d × 48 人日粒度   │        │ document.yaml 12 大域       │
     └─────────────────────┘        └───────────────────────────┘
```

### 3.1 为什么需要后端（而不是纯前端 mock）

部门级口径在真实接口下**无法直接取到**：企业 OpenAPI 的可观测域明确「`groupBy` 不支持 `department`（依赖组织架构，应用身份无该语义，返回 400）」，而 `dashboard/member/data` 提供的是**成员级**数据（含 `departmentIds` / `primaryDepartmentName`）。

因此部门聚合必须由**调用方**完成。本方案把这个职责放在后端，好处：

1. 口径只有一份实现（`metrics.py`），前端不做聚合，避免各页面各算一套；
2. 接入真实接口时只替换 `DataSource`，页面与接口契约不变；
3. 大数据量下聚合发生在服务端，首屏只传聚合结果（overview 响应约 10KB）。

### 3.2 Mock 数据设计

| 项 | 设计 |
|---|---|
| 粒度 | 成员 × 自然日，180 天（可支撑 7/30/90/180 与自定义区间的环比） |
| 组织 | 1 个根 + 6 个部门（平台研发/客户端/数据算法/产品设计/质量保障/企业服务），48 名成员 |
| 真实性来源 | 周末系数 0.17、公司渗透爬坡曲线（0.60→1.15）、新人 45 天爬坡、模型/客户端/插件版本加权分布 |
| 边界场景 | 每部门保留 1 名近 40 天零使用成员（验证空态与提醒）、5% 零代码产出成员、30% 不限量额度成员 |
| 可复现 | 固定随机种子 `20260920`。**日期是独立维度**：`REFERENCE_DAY` 默认取运行当天（保证看板永远是「最近 180 天」），需要字节级复现时用 `AEC_REFERENCE_DAY=2026-09-20` 钉住 |
| 不入库 | 数据集是生成物：入库当天就过期，且 3.5MB blob 进了 Git 历史删不掉。故 `data/` 只提交 `.gitkeep`，clone 后先跑生成器 |
| 一致性 | 所有部门/公司指标由成员日粒度求和，自检脚本校验「部门汇总 == 成员汇总 == 公司总量」 |

## 4. 页面设计

### 4.1 信息架构

```
AI 效能运营台
├─ 用量总览   /overview      组织级 KPI + 趋势 + 部门排行（首屏结论）
├─ 部门效能   /departments   四象限诊断 + 部门明细对比 + 下钻入口
├─ 个人效能   /members       逐人明细 + 效能详情抽屉（核心页）
├─ 额度管理   /quota         风险分档 + 批量/部门级额度调整 + 审计
└─ 指标口径   /metrics       指标字典 + 接口映射 + 已知边界
```

### 4.2 全局筛选条（贯穿所有页面）

固定吸顶在内容区顶部，保证切页不丢筛选：

- 快捷区间：近 7 / 30 / 90 / 180 天；自定义起止日期；
- 部门范围：多选下拉（带人数），选中后全局生效；
- 右侧显示**环比对照区间**（等长紧邻），避免对「和谁比」产生歧义；
- Mock 数据标识 + 刷新按钮 + 最后更新时间。

> 设计要点：把「环比对照区间」明写出来，是这类看板最容易被追问的点（"你这个 +12% 是和什么比？"）。

### 4.3 页面一：用量总览

```
┌ KPI ×8 ────────────────────────────────────────────────────┐
│ Credits消耗(↓好) │ 活跃人数 │ 新增代码行 │ AI生成行          │
│ AI代码占比       │ 采纳率   │ Token消耗(↓好)│ 对话次数        │
└────────────────────────────────────────────────────────────┘
┌ 消耗与 AI 渗透趋势（双轴：Credits 面积 + AI 占比虚线）──┬ 部门消耗结构 ─┐
│                                                        │ 环形图 Top8   │
├ 代码产出结构（堆叠柱：AI 生成行 / 人工编写行）──────────┼ 席位与额度 ───┤
│                                                        │ 席位使用率    │
│                                                        │ 积分余额      │
│                                                        │ 额度周期      │
│                                                        ├ 消耗-产出画像 ┤
│                                                        │ 高耗低产名单  │
├ 部门用量排行（可排序表格，点击下钻）───────────────────┴───────────────┤
└────────────────────────────────────────────────────────────────────────┘
```

设计要点：

1. **KPI 区分方向语义**：消耗类指标（Credits/Token）标注「↓ 为好」，环比上涨显示红色，避免"涨了就是好事"的误导；
2. **每张 KPI 带迷你趋势线**（近 14 天），让单点数值具备趋势语境；
3. **消耗与占比双轴同图**：两者的背离（消耗涨、占比跌）是最有价值的信号；
4. **堆叠柱而非双柱**：直接呈现 AI 行与人工行的结构占比，而非并列两个数；
5. **首屏即可结论**：不点任何按钮就能看到"钱花在哪、产出如何、哪个部门要复盘"。

### 4.4 页面二：部门效能

- **消耗-产出四象限散点**：X = AI 代码占比、Y = Credits 消耗、气泡大小 = 部门人数，叠加中位数分界线；每象限下方给出部门名单与处置建议。
- **消耗趋势（7 日滑动平均）**：抹平周末波动后看真实走势，避免被单日尖峰误导。
- **部门明细表**：活跃/总数、Credits、消耗环比、人均消耗、新增行、AI 生成行、AI 占比（带进度条）、采纳率、人均 AI 行、千行成本、请求失败率；数值列右对齐 + 等宽字体便于纵向扫读。
- **交互**：点击部门名 → 跳转个人效能页并自动按该部门过滤；「加入对比」→ 参与全局部门范围筛选。

### 4.5 页面三：个人效能（核心页）

**筛选区**：关键字搜索、排序字段（新增行/AI 生成行/AI 占比/采纳率/Credits/千行成本/对话次数/活跃天数）、升序降序、最小代码行阈值（不限 / ≥500 / ≥2000 / ≥5000）、部门下拉。

**KPI ×7**：成员总数、有活跃行为、新增代码行合计、AI 代码占比、Credits 消耗、额度超限风险人数、零代码产出人数。

**主表字段**（逐人）：成员（头像+部门）、最近活跃、活跃天数、**新增代码行**、**AI 生成行**、**AI 代码占比**（数值+进度条）、采纳率、对话次数、Token、Credits（含环比箭头）、千行成本、额度使用率、详情入口。

**三张洞察卡**：AI 代码贡献 Top3（标杆）、高消耗待复盘（千行成本最高 Top3）、冷启动名单（窗口内零行为）。

**成员详情抽屉**（点击任意行弹出，右侧 720px 滑出）：

```
┌ 头部：姓名 + 部门 + 风险徽标 + 邮箱/入职/主语言 + 统计窗口 ─────┐
│ 12 项指标网格：新增行/AI行/AI占比(带部门均值)/采纳率(带均值)/       │
│   Credits(环比)/千行成本(带部门均值)/对话数/Token/活跃天数/       │
│   最近活跃/额度使用率/日均AI行                                   │
├ 代码产出与 AI 占比趋势（AI行+人工行堆叠 + AI占比虚线）───────────┤
├ 消耗趋势（Credits + Token 双轴）  ┬ 模型消耗分布（环形）──────────┤
├ 客户端分布                       ┬ 语言分布（含 AI 代码行）──────┤
└ 与部门均值对比（AI占比 / 采纳率 / 千行成本，本人 vs 部门）───────┘
```

设计要点：个人数据一律**带部门均值对照**，避免"孤立数字无法判断好坏"；模型分布用于判断是否用了"过重"的模型（成本治理的常见抓手）。

### 4.6 页面四：额度管理

- **KPI ×6**：已配置限量成员、使用默认额度成员、超限风险成员、用量偏高成员、窗口总消耗、限量子集使用率。
- **批量调整**：勾选成员 → 统一设置新限量 / 设为不限量（对应 `usage/members/quota/update`）。
- **风险分布条**：四档进度条，点击即筛选下方明细表。
- **按部门调整**：选择部门 + 统一限量 → 应用到部门全部成员（对应 `usage/departments/{departmentId}/quota/update`），并给出「会覆盖已单独配置成员」的高影响提示。
- **明细表**：消耗、周期限量、使用率（数值+进度条）、风险标签、快捷调整（消耗×1.25 / 设为不限量）。
- **调整审计**：列出本会话内的额度变更记录（真实环境应替换为企业侧审计日志）。

### 4.7 页面五：指标口径

- 四条不可违反的口径原则（先求和再相除 / 部门=成员之和 / 消耗与产出成对 / 环比等长）；
- 指标字典：按 6 个分组（用量成本、代码贡献、补全采纳、活跃渗透、稳定性体验）列出定义、公式、来源、口径与注意事项，支持分组筛选；
- 接口映射表：场景 ↔ 接口 ↔ 字段 ↔ 注意事项；
- 已知边界：mock 说明、部门聚合原因、代码行口径、提效验证建议、时区与周期、APM 降级。

> 这一页是**可交付性**的关键：业务方对数字产生异议时，能立刻回到定义而不是争论。

### 4.8 视觉与交互规范

| 维度 | 规范 |
|---|---|
| 主题 | 深色专业向（`#0b1020` 底 + 品牌蓝 `#3b6dfb` + 状态色），适合长时间盯盘与投屏 |
| 语义色 | 绿=良好、琥珀=注意、红=风险、灰=无数据；**消耗类指标上涨用红色** |
| 数字排版 | 全站等宽字体 + `tabular-nums`，表格数值右对齐，保证纵向不跳位 |
| 图表 | ECharts，统一 `theme.ts` 取色；面积图用渐变；工具提示深色化 |
| 空态 | 区分「无数据」「指标不可用」「未筛选到」三种语义，均给出下一步指引 |
| 加载 | 骨架屏 + 局部 loading，切筛选不整页闪烁 |
| 自适应 | 三档栅格：桌面 3 列 / 平板 2 列 / 移动 1 列；表格横向滚动 |

## 5. 接口设计

### 5.1 分层

| 层 | 路径 | 说明 |
|---|---|---|
| 本方案扩展（前端直用） | `/api/v1/efficiency/*` | 后端已聚合的效能口径，首屏一次拿齐，避免前端 N+1 |
| 对齐企业 OpenAPI（联调核对 / 二期扩展） | `/api/enterprises/{eid}/dashboard/*`、`/openapi/usage/*`、`/openapi/observability/*`、`/metrics` | 路径与字段严格对齐 `document.yaml` |

### 5.2 扩展接口一览

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/v1/efficiency/overview` | 组织 KPI + 部门排行 + 日趋势（总览页/部门页） |
| GET | `/api/v1/efficiency/members` | 成员明细（支持排序、关键字、分页、部门筛选） |
| GET | `/api/v1/efficiency/member/{memberId}` | 成员效能详情（趋势 + 模型/客户端/语言分布） |
| GET | `/api/v1/efficiency/quota` | 额度视图（限量 + 消耗 + 风险分档） |
| GET | `/api/v1/efficiency/meta` | 数据集元信息 / 额度周期 / 默认额度 / 调整审计 |
| POST | `/api/v1/efficiency/...` | 额度调整复用企业接口路径（见下） |

统一响应包装（与企业接口一致）：

```json
{ "code": 0, "msg": "OK", "requestId": "uuid", "data": { ... } }
```

错误语义：`400` 参数非法（如指标名不在白名单）、`403` 企业隔离/无权限、`404` 未实现、`500` 服务端异常。**查询失败绝不降级为 0**（否则会把"查询失败"渲染成"额度用尽"）。

### 5.3 与企业 OpenAPI 的映射与差异

| 分析场景 | 企业接口 | 本方案处理 |
|---|---|---|
| 成员级代码量与 AI 占比 | `POST /dashboard/member/data` | 直接使用其字段口径；后端补齐派生字段（`__quotaUsageRate`、`__creditsPerKline` 等，`__` 前缀标识扩展） |
| Credits 消耗与限量 | `POST /openapi/usage/members/query` | 取 `totalUsed` + `cycleLimit`，与代码量按 `userId` 关联 |
| 额度调整 | `POST .../usage/members/quota/update`、`.../departments/{id}/quota/update` | 原样透传，仅做前端交互与风险提示 |
| 积分/席位余额 | `GET /openapi/resources/overview` | 直接展示；区分 `credit` / `license` 两类资源 |
| 活跃/对话/补全/生成分析 | `POST /dashboard/analytics/{kind}` | 返回统一的 `DashboardResponse`，可直接驱动 KPI 卡 + 图表 |
| 可观测指标 | `POST /openapi/observability/metric-{summary,trend,records}/query` | 指标名白名单校验；**`groupBy` 不支持 department，部门维度由后端 rollup** |
| 旧看板时序 | `GET /enterprises/{eid}/metrics` | 保留兼容实现，返回 `[时间戳[], 值[]]` 结构 |

**必须注意的差异点**：

1. `groupBy=department` 在企业接口会被拒绝（应用身份无组织语义），部门口径**只能由调用方 rollup**；
2. `usage/members/query` 推荐使用 `userIds`（UUID）而非 `userNames`（全半角/emoji 会导致静默不匹配）；
3. 额度周期的切分以 `cycleMode` 为准，`cycleType` 只是档位标签，不决定周期；
4. 私有化部署未配置 APM 时可观测域返回 404，属预期降级。

### 5.4 前端切换 mock / live

```bash
# frontend/.env.local
VITE_DATA_MODE=mock          # 默认：本地 Python mock 服务
VITE_DATA_MODE=live          # 二期：由后端代理企业 OpenAPI（页面零改动）
VITE_API_BASE=               # 留空表示同源（Vite 代理）
VITE_ENTERPRISE_ID=1234567890
```

页面代码只依赖 `lib/api.ts` 暴露的强类型函数，不出现任何 mock 判断分支。

## 6. 安全、性能与权限

### 6.1 权限（建议的最小模型）

| 角色 | 可见范围 | 可操作 |
|---|---|---|
| 企业管理员 | 全公司 + 全部部门 | 额度调整、导出 |
| 部门负责人 | 本部门（含子部门） | 导出本部门，不可调整额度 |
| 团队成员 | 仅本人 | 不可见他人明细 |

> 注意：企业 OpenAPI **仅支持 admin 开发平台创建的企业级应用（应用身份）调用**，个人 API Key 调用任意接口返回 401。因此 token 必须保存在服务端，**不允许下发到浏览器**。

### 6.2 数据安全

- 看板只展示聚合指标与用量，不展示对话内容；若需引用对话日志（`session-logs`），必须单独授权并记录审计。
- 导出 CSV 仅含指标字段，不含邮箱/工号等 PII（当前 `email` 仅用于详情抽屉展示，可在二期按角色屏蔽）。
- 接口层按 `enterpriseId` 硬隔离，跨企业访问在中间件返回错误。

### 6.3 性能

| 项 | 措施 |
|---|---|
| 首屏 | overview 一次返回 KPI + 部门 + 趋势（约 10KB），避免多请求瀑布 |
| 聚合 | 服务端按「日期 → 记录」建索引后单次遍历；Python 层 7200 条日记录的聚合耗时 <100ms |
| 前端 | ECharts 按需实例化 + `ResizeObserver` 自适应 + 组件卸载 `dispose`；路由级页面拆分 |
| 大数据量 | 二期可将日粒度明细下沉到 ClickHouse/Doris，overview 走预聚合表（天级物化视图） |

### 7.2 验收标准

**数据正确性**

- [ ] 部门汇总之和 == 成员汇总之和 == 公司总量（`server.py --selftest` 自动校验，误差 <0.01）
- [ ] 比率型指标均为「先求和再相除」，与逐人比率平均值不同（可用一个部门手工复核）
- [ ] 换任何时间范围，KPI、图表、表格三处口径一致
- [ ] 无对比基数时展示「无对比数据」而非 0%

**功能完整性**

- [ ] 5 个页面均可访问，筛选条在任意页面切换后保持
- [ ] 部门 → 成员下钻链路可用（点击部门名/表格行）
- [ ] 成员详情抽屉展示 12 项指标 + 4 张图 + 部门均值对照
- [ ] 额度调整（成员批量 / 部门级）调用成功并刷新数据，审计可见
- [ ] CSV 导出内容与页面当前筛选一致

**体验与健壮性**

- [ ] 后端未启动时展示明确错误与启动指引，不白屏
- [ ] 空数据 / 零产出成员 / 不限量成员均有明确语义展示
- [ ] 窗口缩放与侧边栏布局变化时图表自适应不错位

**性能**

- [ ] 首屏（含 mock 数据加载）< 1.5s
- [ ] 切换筛选后数据刷新 < 500ms

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 「AI 代码占比」被当作绩效指标 | 引发刷量、对抗 | 页面显式标注边界；占比与消耗、绝对产出联合展示；不做个人排名结论 |
| 行数受语言/格式化影响 | 跨部门比较失真 | 提供按行/按字符双口径对照；同部门内比较为主 |
| 额度周期与看板窗口不对齐 | 提额决策误判 | 页面标注当前额度周期；额度页以周期口径提示 |
| 真实接口的部门数据可能缺失 | 部门聚合失败 | 聚合层对无部门成员归入「未分配」并显式展示，不静默丢弃 |
| 可观测域在私有化不可用 | 稳定性指标空白 | 空态标注「该指标在当前部署不可用」而非 0 |
| 大企业 10 万级成员 | 接口分页与聚合压力 | 二期引入预聚合表 + 增量同步，前端只读聚合结果 |

## 9. 如何运行（当前 mock 阶段）

```bash
# 1) 生成 mock 数据集（生成物不入库，必须先跑这一步）
python3 backend/app/gen_mock.py
#    需要可复现的数据窗口时：AEC_REFERENCE_DAY=2026-09-20 python3 backend/app/gen_mock.py

# 2) 自检后端接口与口径一致性
python3 backend/app/server.py --selftest

# 3) 启动 Mock API（默认 127.0.0.1:8000）
python3 backend/app/server.py --port 8000

# 4) 启动前端（默认 127.0.0.1:5173，已配置 /api 代理）
cd frontend && npm install && npm run dev
```

生产构建：`cd frontend && npm run build`，产物 `frontend/dist` 可直接由 `server.py` 同源托管（无需额外静态服务）。
